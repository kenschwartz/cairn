# Cairn TODO

Open design questions and deferred work. Phase 1-3 are build-ready; the items here are Phase 4 and beyond, or decisions deferred until they block.

## Phase 4 - tags (the `Q004-*` set)

Tag NORMALIZATION at write time is decided (the slug-plus-slash rule in DESIGN.md "Tags") and ships in Phase 1. What is NOT decided is the Phase 4 command surface and the index format. `T004-implementation` is blocked until these resolve; then DESIGN.md "Tags" gets updated with the accepted answers.

- **Q004-1 - Phase 4 command surface.** Decide the exact commands: does `cairn tags` list tags (with counts)? Is there `cairn tag rename <old> <new>`, `cairn tag merge`, `cairn tag delete`? Which are read-only vs mutating, and which phase block each lands in.
- **Q004-2 - `indexes/tags.md` format.** The generated tag index: one section per tag with backlinks to the notes carrying it? Alphabetical, or by frequency? Regenerated by which command, and is it committed (tracked, content-pinned like the dashboard) or gitignored?
- **Q004-3 - Tag mutation semantics.** When a tag is renamed across the vault, what is the contract: rewrite every `tags:` frontmatter line and every inline `#tag`? How are conflicts handled (a rename collides with an existing tag)? Is a mutation one commit or many?
- **Q004-4 - Multi-file write safety.** A tag rename touches many files in one operation. Rules needed: atomicity (all-or-nothing vs best-effort), partial-failure recovery (a write fails mid-rename - what state is the vault left in, and how does `cairn doctor` or a journal repair it), and the relationship to auto-commit (does a mutation auto-commit, and with what message).
